# Детектор фишинговых сайтов по URL и содержимому

Учебный проект по дисциплине «Программирование (Python)».
Направление — компьютерная безопасность.

## Описание проекта

Фишинговые сайты копируют внешний вид доверенных ресурсов, поэтому
узнать их по одному URL почти невозможно: домен может содержать
название известного банка, а страница — его логотип и форму входа.
Проверка самого адреса даёт лишь грубый фильтр, а ручной разбор каждой
страницы не масштабируется. Отсюда задача — автоматически оценить
страницу целиком и объяснить пользователю, что именно в ней смутило.

**Цель:** разработать конвейер, который по URL определяет, является ли
страница фишинговой, и выдаёт мотивированный вердикт.

**Задачи:**

1. Реализовать быструю проверку URL как первый рубеж отсечения.
2. Реализовать алгоритмический разбор структуры страницы в реальном
   браузере: формы, адрес отправки данных, iframe, сертификат.
3. Реализовать оценку страницы локальной языковой моделью.
4. Свести результаты этапов в единый вердикт с объяснением.

**Принципиальное ограничение.** Система работает на стороне клиента и
не перехватывает сетевой трафик. Открывая страницу в управляемом
браузере, мы получаем уже расшифрованное содержимое DOM, поэтому
анализ идёт по данным, которые реально видит пользователь. Внешние
API не используются: подозрительный HTML с чужими парольными формами
не должен покидать машину пользователя.

**Ожидаемый результат:** для введённого адреса — оценка риска от 0 до
100, уровень (низкий, средний, высокий, критический), список
конкретных сработавших признаков и рекомендация пользователю.

## Что это

Конвейер из четырёх этапов, который получает URL и выдаёт вердикт:
подозрительный фишинг, требует проверки или чисто. Каждый этап работает
со своим типом данных, общий контракт описан в `src/phishguard/models.py`.

| Этап | Модуль | Что делает | Исполнитель |
|------|--------|-----------|-------------|
| 1 | `url_checker.py` | быстрый фильтр URL: IP вместо домена, сокращатели, punycode, имитация брендов, глубина поддоменов | модуль №1 |
| 2 | `page_analyzer.py` | Selenium/Playwright: DOM, формы, `action`, iframe, сертификат, балл риска по правилам | модуль №2 |
| 3 | `llm_judge.py` | локальная LLM получает компактные признаки и отвечает «фишинг или нет» | модуль №3 |
| 4 | `synthesizer.py` | сводит баллы этапов в один вердикт и текст для пользователя | модуль №4 |

## Установка

```bash
git clone <url репозитория>
cd <папка>
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r requirements.lock.txt
```

`requirements.txt` хранит прямые зависимости, `requirements.lock.txt` —
их точные версии. Ставьте по lock-файлу, тогда у всех одинаковое
окружение и «у меня не запускается» не возникает.

## Запуск

```bash
python main.py "http://bit.ly/sberbank-login"
python main.py "https://sberbank.secure-login.ru/verify" --json
python main.py "https://example.com" --no-page --no-llm
```

Код возврата: `0` — риск низкий, `2` — высокий или критический.

Если вместо русского текста в консоли видны «кракозябры», это кодовая
страница терминала, а не ошибка программы:

```bash
chcp 65001
python main.py "https://example.com"
```

или разово `set PYTHONIOENCODING=utf-8`. Файл отчёта в JSON всегда в UTF-8.

Пока модули №2 и №3 не дописаны, они помечаются как пропущенные, и
программа всё равно выдаёт вердикт. Это сделано намеренно: сквозной
прототип должен работать с первого дня, а этапы добавляются по одному.

## Локальная LLM

```bash
# https://ollama.com
ollama serve
ollama pull qwen2.5:7b-instruct
```

Модель скачивается один раз и работает офлайн. Облачные API не
используются намеренно: отправлять подозрительный HTML стороннему
сервису значило бы отправить чужие парольные формы.

## Разработка

```bash
pytest -q
```

Ветка `main` неприкосновенна. Каждый работает в своей ветке
`feature/url-checker`, `feature/page-analyzer` и т.д., сливает через
pull request. Никто не правит чужие файлы, кроме `models.py` — этот файл
меняется только после общего обсуждения, потому что от него зависят все.
